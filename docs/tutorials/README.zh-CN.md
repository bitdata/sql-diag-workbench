# 用示例数据库练习 SQL 数据排查与性能分析

[English](README.md) | 简体中文

这组教程从三个问题开始：订单为什么少了、为什么重复、金额为什么算大了。随后使用 employees 和 AdventureWorks 的真实表，练习历史数据关联和执行计划分析。

每个 SQL 文件包含多个独立查询。**每次只复制一个查询到工作台**，将 A、B 分别保存在不同标签页，便于保留现场和比较。所有示例均为只读查询，不需要建表、导入数据或修改索引。

## 共同操作：先建立一条证据链

1. 新建查询标签页，选择连接和方言，粘贴 A 查询，点击 **解析**。
2. 选根节点查看完整查询；沿树中可用的拆解操作展开 JOIN、WHERE、聚合或子查询。仅解析但不展开时，调查可能只有根节点证据。
3. 在数据模式执行根查询，再执行相关片段，核对结果和业务预期。树中独立执行的片段说明逻辑结果，不代表原查询物理算子的运行成本。
4. 在 **数据** 模式的结果区域点击 **行追踪**，选择 **存在性** 或 **数量**。键名必须是结果中实际输出的列标签，数值键选 `DECIMAL`。Oracle 通常显示大写标签，例如 `ID`，应照结果表头填写。
5. 阅读每步的结果与范围。跳过、键未投影、超时和失败都表示没有取得这一步的证据，不能当成零行。若当前图不足，继续展开，或执行下面指定的对照查询。
6. 将 B 查询放到新标签页，分别执行，再用 **比较** 并排核对。使用“编辑 SQL 并新建标签页”也可保留 A；来源链接回到来源标签页，根节点表示当前标签页的完整 SQL。

这里的“预期最大值”由业务定义。例如一订单一行可填 1；一订单一标签则应使用订单号加标签的复合键。工具不会替你决定业务粒度。

### 操作入口与核对方法

以下以片段树视图为准。节点左侧的三角只负责展开或折叠已有子节点；**生成新片段需要调用拆解规则**。

| 目的 | 具体操作 | 核对点 |
| --- | --- | --- |
| 生成拆解片段 | 右键目标节点，或点击节点的 `⋯`，等待可用规则加载；选择 **移除子句**、**拆分 JOIN** 等规则 | 树中出现新片段；根节点的原查询仍然保留 |
| 查看某个片段 | 单击节点，阅读编辑器 SQL | 先核对 WHERE、JOIN、投影列实际发生了什么变化，再执行 |
| 执行当前片段 | 选中节点后点击 **执行片段**；根查询可用 **执行 SQL**；也可按 `Ctrl+Enter` 执行当前编辑器 SQL | 检查表头、行数与值；不要把上一次执行结果当成本节点结果 |
| 调整调查条件 | 已有追踪结束后先点 **清除**，回到输入表单；修改模式、键或预期最大值，再点 **追踪** | **重新追踪**沿用上次提交的图和条件；拆解图改变后也应清除后再提交 |
| 新建改写版本 | 右键指定节点，选择 **编辑 SQL 并新建标签页**，编辑后保存；也可直接新建标签页粘贴 SQL 文件中的 B | 要改完整查询时先选根节点，避免误将某个简化片段当成完整查询 |
| 获取执行计划 | 选择目标查询的根节点，切换 **性能**，点击 **分析**打开菜单，再选择 **估算计划**或 **实际计划 (ANALYZE) · 会执行查询** | 单击分析按钮只展开菜单；选菜单项后才采集。结果区域的 **计划**用于查看计划，**诊断**用于查看线索 |

子片段名称可能仍显示英文，如 `Remove WHERE`，或带作用域信息。下面均同时写明要检查的 SQL 特征，不以节点位置或编号识别片段。未出现指定规则、候选不可用或执行失败时，记录实际提示，暂停该条核对；不要自行把不同片段当成同一步骤。

## 案例 1：用了 LEFT JOIN，为什么订单 4 还是不见了？

**业务约定**：保留全部订单，只补充东区客户的信息。

固定数据有订单 1、2、3、4。订单 1、2 属于东区，订单 3 属于西区，订单 4 的客户不存在。A 把 `c.region = 'east'` 写在 WHERE 中。

### 第一阶段：拆分定位，不改写原查询

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 1 | 打开本数据库的 `01-missing-order.sql`，只复制 A 查询到新标签页；选择连接与方言 | SQL 同时包含 `LEFT JOIN`、`WHERE c.region = 'east'` 和 `ORDER BY o.id` |
| 2 | 点击 **解析**，选择树的根节点，在数据模式执行 | 结果为 `(1,east)、(2,east)`，没有订单 4 |
| 3 | 右键根节点 → **移除子句**，展开新生成的子节点 | 可能同时生成移除 WHERE、移除 ORDER BY 等实验；它们是不同的候选，不是按顺序逐项删除 |
| 4 | 选择 `Remove WHERE` 对应片段，阅读 SQL | `WHERE c.region = 'east'` 已移除；`LEFT JOIN ... ON o.customer_id = c.cid` 保留；不要选仅移除 ORDER BY 的片段 |
| 5 | 执行该片段 | 结果为 `(1,east)、(2,east)、(3,west)、(4,NULL)`；此步已足以证明 WHERE 前后订单 4 的存在性发生变化 |
| 6 | 保持当前图，点击 **行追踪**；调查模式选 **存在性**，列填结果中的 `id` / `ID`，类型选 `DECIMAL`，值填 `4`，点击 **追踪** | 提交片段数应大于 1；根查询不含 4，移除 WHERE 的片段含 4。其他片段可能跳过，逐项读原因 |
| 7（补充） | 若还要核对订单源：先点击 **清除**清理已结束的追踪，右键“移除 WHERE”片段 → **拆分 JOIN**；选保留订单侧、移除客户侧的候选，先读 SQL 再执行 | 该候选不再 JOIN 客户，仍输出订单 `id`，应含 1、2、3、4；移除客户列后不应要求仍有 `region`。若不可用，记录限制；步骤 5 的证据仍然成立 |

**本阶段结论**：在移除 WHERE 的独立实验中，LEFT JOIN 保留订单 4，`region` 为 NULL；原查询的 WHERE 不接受这行。订单 3 也因地区不是 east 被排除。这里定位的是查询逻辑边界，不能当成执行计划的物理步骤顺序。

### 第二阶段：改写验证，另存 B 查询

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 8 | 回到 A 的根节点，右键 → **编辑 SQL 并新建标签页**；把地区条件从 WHERE 移入 ON。也可新建标签页，直接粘贴 SQL 文件中的 B | 条件为 `ON o.customer_id = c.cid AND c.region = 'east'`，不再有该 WHERE 条件；A 标签页保留 |
| 9 | 在 B 标签页解析并执行根查询 | 返回 `(1,east)、(2,east)、(3,NULL)、(4,NULL)`；与步骤 5 相比，订单 3 的 region 由 west 变为 NULL |
| 10 | 回到 A、B，分别查看根查询与结果，按下面的业务约定核对 | B 保留四张订单且只补充东区信息；A 仅保留东区订单。不要把步骤 5“无 WHERE”片段直接当成 B，两者语义不同 |

如需逐项打勾，可使用：`[ ] A 两行`、`[ ] 移除 WHERE 后四行且订单 3 为 west`、`[ ] 追踪 4 的证据一致`、`[ ] B 四行且订单 3 为 NULL`、`[ ] A 原查询保留`。

**对照**：B 将地区条件移到 ON，返回 `(1,east)、(2,east)、(3,NULL)、(4,NULL)`。这符合上述业务约定。若业务原本只要东区订单，A 的两行结果就是合理过滤，不能仅因“丢行”判定 SQL 错误。

**亮点**：从“结果少了”缩小到一个具体键和一个过滤边界，而不是反复删改整条 SQL。

## 案例 2：存在性正常，为什么订单仍然重复？

**数据来源**：教程内联数据，不读取业务表。使用对应方言的 `02-duplicate-order.sql`。

**业务约定**：列出有标签的订单，每个订单一行。订单 1 有 red、blue 两个标签；订单 3 有 green 标签。

### 第一阶段：拆分与数量调查

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 1 | 新建标签页，粘贴 A，选择连接与方言 → **解析** → 选择根节点 → 数据模式执行 | 返回 `1、1、3`；订单 1 出现两次 |
| 2 | 右键根节点 → **拆分 JOIN**，选保留订单侧、移除标签侧的候选；先读 SQL 再执行 | SQL 不再 JOIN 标签；订单 1 在这个独立片段中只有一行。无可用候选时记录限制 |
| 3 | 点击 **行追踪** → **存在性**，列填实际表头 `id` / `ID`、类型 `DECIMAL`、值 `1` → **追踪** | 根查询找到该键；存在性正常并不能排除重复 |
| 4 | 结束后点 **清除**，改选 **数量**，重填同一键，勾选预期最大值并填 `1` → **追踪** | 根查询匹配数为 2；与订单侧一行形成对照 |

**本阶段结论**：每个标签生成一行配对，订单号不再是最终结果的唯一键。

### 第二阶段：改写与业务粒度对照

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 5 | 回到 A 根节点 → **编辑 SQL 并新建标签页**，改为文件中的 B；或直接新建标签页粘贴 B；解析执行 | EXISTS 仅判断有无标签，结果为 `1、3`，A 保留 |
| 6 | 新建标签页粘贴 C，解析执行 | 输出 `(1,blue)、(1,red)、(3,green)`，三条订单标签组合 |
| 7 | 在 C 的行追踪中选数量模式，填 `id=1`（`DECIMAL`），点 **添加键**，填 `tag=red`（`TEXT`）；预期最大值 1 → **追踪** | 复合键只匹配一行，说明订单加标签的粒度下结果合理 |

**核对清单**：`[ ] A 三行`、`[ ] 存在性找到 1`、`[ ] 数量为 2`、`[ ] B 两行`、`[ ] C 复合键一行`。

**结论与亮点**：先确定业务粒度，再判断是否重复；不要先加 DISTINCT 掩盖关联关系。

## 案例 3：客户只出现一行，金额为什么翻倍？

**数据来源**：教程内联数据，使用 `03-inflated-total.sql`。订单 1 金额 100，有两个标签；订单 3 金额 70，有一个标签。

**业务约定**：按客户统计“有标签订单”的金额，每张订单只计一次；没标签的订单 2、4 不纳入。

### 第一阶段：核对汇总与明细

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 1 | 新建标签页粘贴 A → **解析** → 选择根节点 → 数据模式执行 | 返回 `(10,200)、(20,70)`，客户 10 金额偏大 |
| 2 | **行追踪** → **数量**，列按实际表头填 `customer_id`、类型 `DECIMAL`、值 `10`，预期最大值 1 → **追踪** | 根查询只有一条匹配行；此检查无法证明 total 正确 |
| 3 | 另建“明细核对”标签页复制 A；手工将 SELECT 改为 `o.id, o.customer_id, o.amount, t.tag`，删除 GROUP BY，ORDER BY 改为 `o.id, t.tag` | 这是显式改写的核对查询，不是自动“移除聚合”拆解；JOIN 条件保留 |
| 4 | 解析执行明细查询 | 订单 1 的两行 amount 均为 100，标签分别 blue、red；订单 3 为 70 |

**本阶段结论**：JOIN 在聚合前复制了订单金额；最终每客户一行仍然可能算错。

### 第二阶段：按订单粒度改写并验证

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 5 | 在新标签页粘贴文件中的 B，解析并执行根查询 | EXISTS 保持订单粒度，返回 `(10,100)、(20,70)` |
| 6 | 回看 A、明细核对、B 三个标签页 | 200 的来源可由两条 100 解释；B 的 100 符合每单只算一次的业务要求 |

**核对清单**：`[ ] A 客户 10 金额 200`、`[ ] 客户数量检查仍正常`、`[ ] 明细两条 100`、`[ ] B 金额 100`。

**结论与亮点**：数据正确性包含数值正确。不能用 `SUM(DISTINCT amount)` 通用修复，两张不同订单可能有相同金额。

## 案例 4：employees 的 5 名员工，为什么查出 88 行？

**数据来源**：datacharmer/test_db 的 employees 数据模型，读取实际 `employees、salaries、titles` 表；PostgreSQL 使用 `public`，MySQL 使用 `employees` schema。使用 `04-employee-history.sql`。

**业务约定**：查看员工 10001～10005 的当前工资和当前职称；A 只按员工号关联两张历史表。

### 第一阶段：拆分历史关联并调查数量

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |
| 1 | 粘贴 A 到新标签页，选择对应连接与方言 → **解析** → 根节点 → 数据模式执行 | 当前样例库返回 88 行，工资开始日期和职称开始日期形成组合 |
| 2 | 右键根节点 → **拆分 JOIN**，按 SQL 选择保留 `e.emp_no` 与工资历史、移除职称历史的候选，执行 | 每名员工可能有多条工资历史；多表关联可能需继续对候选调用规则，不能按节点编号识别 |

## 案例 7：AdventureWorks 的订单金额，为什么大了 12 倍？

**数据来源**：Microsoft sql-server-samples 中的 AdventureWorks OLTP 数据模型，读取实际 `Sales.SalesOrderHeader`、`Sales.SalesOrderDetail`。使用 `07-adventureworks-total.sql`。

**业务约定**：统计有明细订单的应付金额，订单头 `TotalDue` 每单只累计一次，固定检查订单 43659。

### 第一阶段：从汇总回到明细数量

| 步骤 | 具体操作 | 应看到 / 应核对 |
| --- | --- | --- |

| 2 | 新建明细核对标签页粘贴 B，解析执行 | 12 条明细，每行重复同一笔 `TotalDue` |

## 案例 9：284 万条工资历史中，为什么同一份汇总有不同工作量？

**数据来源**：datacharmer/test_db 的实际 salaries 表，当前两库各 2844047 行。使用 `09-large-salary-scan.sql`，不额外造数据或修改索引。

### 性能测量记录方法（案例 5、6、9 共用）

1. A/B 使用同一数据库、数据范围、连接、超时和结果上限，保持数据稳定；记录数据库版本、索引和计划。实际计划会执行 SELECT。
2. 先各执行一次热身并单独记录，随后按 `A → B → B → A` 顺序做三轮，保留全部原始值，再分别计算 A/B 的中位数与最小/最大值。不要只挑最快一次。
3. 数据库原生执行时间和工作台总耗时分栏记录；计时口径一致后再比较。实际计划采集本身有开销，受其影响的数字不等同普通执行时间。
4. 不主动清空共享数据库缓存。索引与统计信息不一致、并发负载变化、超时、取消或计划采集失败时，说明条件，不能记成正常运行耗时。
5. 如果差异太小或顺序改变就反转，结论写“当前条件下收益不稳定”；案例 6 正是练习这种判断。当前文档留存的是单次计划采样，尚未按此流程完成多轮基准。

## 怎样读诊断结论

- **待确认**：规则发现了值得调查的线索，尚未证明是根因，也不表示后台仍在处理。HIGH / MEDIUM / LOW 表示优先级；置信度不等于根因概率。
- **验证**：仅在该提示提供验证入口且数据库支持时使用。已确认或已反驳只适用于被验证的具体判断和这次观测；许多计划结构观察没有验证按钮。
- **分析不完整 / 跳过 / 失败**：存在证据缺口，应先读原因。没有提示也不能证明查询正确。
- **A/B**：并排结果便于核对，不会自动形成受控性能实验。独立执行也不保证共用一个数据快照；并发写入时要考虑数据变化。

建议每个案例记录五项：业务粒度、预期结果、实际证据、改写后的结果、尚未确定的部分。先证明结果符合业务，再评估性能。
